# 研究室メンバーへの配布と初回利用

このフォルダには制作手順、入力票、中間発表型と短い研究発表型の構成・視覚設定、2種類の表紙、CPS LABのロゴ、架空研究の通し作例、編集可能な視覚作例、生成・描画・検査コードをまとめている。作成者の過去チャット、個人メモリ、研究リポジトリへのアクセスは不要。

## 導入

初めて使うメンバーは [READMEの導入手順](../README.md#導入) を上から実施する。GitHubからのクローン、Git・Node.js・uv・LibreOffice・フォントの導入、クライアントへの登録、初回試験を記載している。

- スキルは `SKILL.md` だけでなく、`references/`・`assets/`・`scripts/`・`agents/`・依存定義・lockファイルを含むフォルダ全体で配布する。
- CodexとOpenCodeの共通配置先は `~/.agents/skills/research-presentation-slides/`。Claude Codeには `~/.claude/skills/research-presentation-slides/` から同じ本体を参照するリンクを作るか、その場所へ本体を置く。
- 特定研究のプロジェクトだけで使う場合は、プロジェクト内の `.agents/skills/`、Claude Codeでは `.claude/skills/` を使う。個人用とプロジェクト用のどちらかを選ぶ。同名の古いコピーを複数の探索先に残さず、必要な旧版は探索対象外へ保存する。
- `.venv/`・`node_modules/` は受取人のPCで `uv sync --frozen`・`npm ci` により作り、他OSからコピーしない。制作物・私的素材は利用者の研究フォルダへ保存する。
- Codexは `$research-presentation-slides`、OpenCodeは自然文で「research-presentation-slides スキルを読み込んで」、Claude Codeは `/research-presentation-slides` で明示的に開始する。認識しないときは配置先・権限・同名の重複を確認し、新しいセッションで読込み元と版を確認する。

クライアントの配置・検出方法は [Codex](https://learn.chatgpt.com/docs/build-skills)、[OpenCode](https://opencode.ai/docs/skills/)、[Claude Code](https://code.claude.com/docs/en/skills) の公式仕様に従う。これらのローカル導入は、クラウド実行や別PCへ自動で同期されることを意味しない。

## 最初の依頼例

研究資料があるワーキングディレクトリでエージェントを起動し、次を渡す。エージェントが直下と既存のサブディレクトリから関連資料を確認するため、入力用のフォルダ構成やファイル名を揃える必要はない。特定の資料のパスや参照範囲を指定した場合はそれを優先し、元の配置を保つ。スキルの導入先へ資料を移す必要はない。

```text
research-presentation-slides スキルを読み込んでください。
読込み元と版を示し、references/sharing.md に従って制作環境を確認してください。
PPTX生成・描画と、選択モデルから使える画像生成・画像閲覧を分けて確認してください。

このワーキングディレクトリにある資料を、既存のサブディレクトリも含めて確認し、
今回の研究に関連する資料・素材を元の配置のまま入力に使ってください。
10分の研究発表、聴衆は専門分野の異なる大学院生、言語は日本語です。
発表者・所属：［氏名・所属］
掲載する連絡先：［メール・URL、または掲載しない］
保存先：presentation/my-talk/
短い研究発表型（cps-workshop）、表紙タイプA、フッター横線なし。
実装・評価が未実施の部分は計画として扱ってください。
まず入力資料を整理し、スタイルと企画書を提示してください。
```

途中から使う場合は、確認済みの企画書・スタイル・制作記録と基準版を渡し、「今日はアウトラインまで」と対象を指定する。分かる範囲だけ伝えればよく、制作者が [入力票](../assets/input-brief.md) の情報を資料から整理して必要な不足だけを確認する。使用者がJSONや生成コードを書く必要はない。

本文は `cps-midterm`／`cps-workshop` の構成・視覚設定に従い、表紙選択では切り替わらない。表紙タイプBは背景動画と静止ポスターを指定する。実装・定量結果のない研究にも、計画・概念を説明する型を選ぶ。

## 工程ごとに必要な能力

| 工程 | 必要な能力 | 利用できない場合 |
|---|---|---|
| 企画書・アウトライン・構成 | 日本語の文章作成、提供資料の読取、ファイル編集 | 読めない箇所を特定し、取得できた根拠だけで下書きを作る |
| 新しいスタイルの抽出 | PPTX/PDFの読取、ページ表示、画像資産確認 | 同梱プロファイルなら元PPTXなしで開始できる。新規参照の未確認部分を残す |
| 画像素材・完成イメージの生成と編集 | 選択モデル・接続済みツールから利用可能な画像生成・編集機能 | 用途・素材・寸法等の制作指示を保存し、不足を明示して対応機能を用意する。必要な画像や完成イメージのレビューを省略しない |
| 編集可能PPTX制作 | 公開ツール経路ではNode.js 20以上、PptxGenJS、sharp、Python 3.10以上、利用するフォント | 原稿と素材を整え、必要な依存を導入して再開する。画像だけのPPTXへ変更しない |
| 最終検証 | LibreOfficeまたは対応するPowerPoint、PyMuPDF、Pillow、ページ画像を閲覧できるモデル・ツール、ZIP/XML検査 | 不足を記録する。全ページ画像の実際の確認を省いて完成と断言しない |
| 実際の登壇動作 | 発表先で使用するPowerPoint等 | 編集操作・動画再生・スライドショー等を、静止描画から独立した未検証事項として引き継ぐ |

## 画像生成の選び方

画像生成の提供者やモデルを固定しない。OpenCode・Claude Code・Codexそれぞれで選択したモデルが、現在接続されているツールを含めて何を実行できるか確認する。モデル名、画像入力への対応、言語モデルのAPIキーだけで画像生成も可能とは判断しない。

スキルは画像ごとに、用途、伝えたい内容、参照素材、必要な寸法・比率、スタイル、読みやすさ、保持すべき要素、実物・実測との違いを渡す。実物の証拠として必要な写真は利用者提供の写真を使い、生成画像で偽装しない。文字・表・チャート・正確な図は要求に応じたPPTXネイティブ要素で制作する。新規画像制作、既存素材の利用、ネイティブ作図、最終PPTXの表示検証レンダーを混同しない。

生成後に画像を開いて用途と整合するか確認し、完成イメージは全ページを表示順に収めた1枚の一覧画像として提示する。対応していない機能や外部サービスの契約・権限・利用料金が必要な場合は明示する。特定提供者のAPIキーを全メンバーの必須設定にせず、個人の秘密情報を配布物や生成記録へ含めない。

## 制作基盤と環境記録

通常は公開ツールの `--backend portable` を使う。ロックした依存の導入後に [doctor.py](../scripts/doctor.py) を `--backend portable --strict` で実行し、環境記録を研究作業先へ保存する。Node依存、Python依存、レンダー手段、フォントの不足を直し、再確認する。コマンドと入出力は [再生成と検査](generation.md) に従う。

Codexの `Presentations`・`load_workspace_dependencies` 等がある環境では、従来の `--backend codex` も利用できる。この経路の `@oai/artifact-tool` とhelperは公開経路の必須依存ではない。他のエージェントにCodexのツールがあると仮定せず、利用する経路の実パスと版を記録する。個人のキャッシュパスを配布物へコピーしない。

uv・ni・Nix等は各環境の管理方針に従う。READMEのuv手順以外を使う場合は、対応するPython仮想環境へ必要ライブラリを導入し、解決された版を記録する。Intel Macや特定個人のツールを全メンバーの必須設定にしない。外部パッケージ・モデル・対象アプリの利用権限は配布に含まれない。

doctorの成功は、利用中モデルの画像生成・画像閲覧、使用者レビュー、研究の意味、全ページ個別目視、対象アプリの実操作を証明しない。それぞれを実際に確認して記録する。クライアントからスキルを読めたこと、生成スクリプトが動いたこと、対話を含む全工程を完了したことも別に扱う。各クライアントの未実施試験は未検証のまま残す。

## 初回の品質合わせ

- [通し作例](worked-example.md) で、根拠から主張と図へ変換する方法を確認する。
- READMEの固定入力試験を実行し、自分の環境で最終PPTXから全ページを描画して1枚ずつ確認する。既存の `validation.json` を新規出力の検証結果へ流用しない。
- [視覚作例](visual-reference.md) のPPTXを開き、文字・図形・表・チャートを編集できるか確認する。同梱の表紙タイプBは静止レイアウト見本で、背景動画を含まない。
- 今回の代表ページを同じスタイルの見本と並べ、文字階層・余白・図の大きさを比較する。
- 使用したスキル版、制作ツール、取得できるモデル情報、フォント、確認したアプリ、最終PPTXと検証画像のhashを制作記録に残す。

全く同じ画像や文章になることを合格条件にはしない。研究資料と発表目的に合わせながら、根拠・論理・可読性・編集可能性の [共通完成基準](quality-standard.md) を満たす。配布ZIPの作成と他者への送信は別の操作であり、送信・公開は利用者が指定した範囲で行う。

## 必ずレビューを受ける3か所

企画書 → 使用者レビュー・了承 → アウトライン → 使用者レビュー・了承 → スライド構成と図 → 完成イメージ画像 → 使用者レビュー・了承 → 編集可能なPPTX。各レビューで停止し、修正版も再レビューする。一括依頼でも省略しない。使用者本人が特定工程の省略を明示したときは、その対象と基準版を記録する。

固定入力による技術試験では、どのレビューが対象外かを記録し、架空の使用者了承を作らない。検証対象は最後に生成したPPTXと対応する画像・記録に限定し、別OS・別アプリ・別モデルにも同じ結果を保証しない。
