# スタイル・企画書・アウトライン

## スタイルを作る／適用する

まず、参照PPTXの役割を「研究内容の資料」「見た目の基準」「文体の見本」から独立に選ぶ。複数を兼ねてよく、依頼から明確なら聞き直さない。内容や文体の資料から自動的に配色や構成まで継承しない。文体だけを参照する場合は可視テキストを読み、以下の視覚仕様の抽出は不要。既存ガイドを使う依頼なら、色・フォント・表紙等の今回の設定を記録して再利用する。

文章を作る前に [使用者に合わせた文体](writing-style.md) を読み、現在の環境で参照可能な本人のメモリと本人修正済みの資料から、`style.md` の文体欄を確認・更新する。資料の用途と今回の聴衆に合わせ、研究発表のタイトル・本文・発表メモへ適用する。

新しいPPTXから見た目を抽出する場合：

1. 現行 `Presentations` スキルのテンプレート参照手順を読む。全スライドの一覧と代表ページの実寸表示を確認し、マスター・レイアウト・テーマ・個別書式を照合する。表紙だけから全体を推測しない。
2. 比率・実寸、余白・グリッド、文字階層、色の役割、ロゴの原画像と余白、フッター、ページ番号、図表の共通表現を抽出する。
3. 表紙・章扉（中扉）・通常本文・図写真中心・結果・まとめ・補足を分ける。章扉のロゴ位置や線の有無を本文レイアウトと混同しない。
4. 参照PPTXの実測値と、今回の投影条件で使う運用値を分ける。サイズ変更では座標と寸法を同じ比率で変換する。フォントの存在を確認し、代替が必要なら差を記録する。
5. `style.md` に再利用可能な規則と今回の設定を残す。正本ロゴを保ち、派生コピーには出所を記録する。新規スタイルは代表的な表紙・本文・結果・章扉で見た目を提示する。既存スタイルに十分な例があれば重複生成しない。

既定は [cps-lab-style.md](cps-lab-style.md) の `cps-midterm`。短い研究発表には `cps-workshop` を選び、構成と視覚を研究入力から分離する。表紙だけ `type-a`／`type-b` の2択で確認し、`style.md` と制作記録に残す。表紙タイプAなら研究対象の写真、表紙タイプBなら背景動画と静止ポスター、再生環境を確認する。素材が足りなくても本文の検討は進め、未提供素材を実証写真・動画として捏造しない。明示された別テンプレートにはその指定を優先する。

## 企画書

企画書の目的は、今回の発表が「どんな問題から、何を試し、何が分かり、次へどう進むか」を定めること。世界観・作戦・成果・教訓を整理し、結論を選ぶ。これらは検討用の分類であり、そのままスライドの章名やタイトルへ転記する指定ではない。以下は記載上の構造であり、資料が揃っている順やユーザーの関心に沿って対話順を変えてよい。

### 世界観

| 項目 | 書く内容 |
|---|---|
| 現状 | 聴衆が研究の出発点として理解できる社会・技術・研究領域の状況 |
| 理想 | 現状の先にある望ましい未来。今回の研究期間に達成する約束とは分ける |
| 課題 | 研究期間内に目指す具体的なゴール。理想へどの程度近づけるか |
| 障害 | 今回挑む問題・マイルストーン。従来難しかった理由と、解決が課題へ貢献する経路 |

新規性は関連研究で確認できる差から述べる。「未開拓」「初めて」を根拠なしに使わない。聴衆が必要な前提を理解した段階で、「誰の、どんな判断・行動・作業に何がうれしいか」を早めに示す。研究で目指す便益と、確認済みの効果は動詞と時制で区別する。

長期の目標から現在の検討へ絞るときは、何を段階的に進めるのかを資料から選ぶ。例えば「将来試したい利用場面→まず扱う限定された場面」なら、その場面を選ぶ理由をつなぐ。すべてを「研究全体の課題→今回の課題」という別の研究課題へ置き換えない。ワークショップ等では、提出済みの成果、現在検討している案、参加者と議論したい問いを整理し、未検証の案を成果として埋めない。

### 作戦

各作戦に次を記載する。

- 目標：進捗を確かめる目印。
- 手段：目標に到達する方法。システム構成、実装上の工夫、評価方法も含めうる。
- 判定する証拠：何を見れば到達点が分かるか。
- 短い表現：手段と目的の関係が分かるように書く。「〈手段〉による〈目的〉」は整理の一例であり、全見出しの型にしない。

事前の成功基準がなかった研究に、結果を見てから数値閾値を付け足さない。未実施の方法は計画として区別する。

### 成果

作戦と1対1の対応を作り、各作戦に「主要な結果 → 主要な知見 → 主要な考察」を書く。

- 結果：実際に確認できた事実。条件、標本、単位、期間を添える。
- 知見：結果からどこまで分かるか。
- 考察：意味づけ、解釈、次へつながる判断。事実と混同しない。

成果のない作戦は未実施・未検証として残し、架空の結果で欄を埋めない。計画中心の発表では、既存の予備結果と予定する検証を分けて構成する。

### 教訓と結論

教訓は以下の観点から整理する。該当しない分類の内容を水増ししない。

1. 攻略の肝と進捗
2. 明るい将来展望
3. 懸念と弱点
4. 今後の課題

結論（Main findings）には、この研究の証拠と経験を踏まえて次に挑む人へ渡せる主要な知見・教訓を選ぶ。副次的成果は補助へ下げる。結論は採用したまとめ／サマリへ反映し、独立した「結言」章を必須にしない。

### この段階の確認

- 世界観から今回の障害へ絞れるか。
- 作戦・成果・教訓がつながり、実測と展望が分かれているか。
- 聴衆へ最終的に何を持ち帰ってほしいかが明確か。

一度に全体を判断しづらい場合は世界観などの一まとまりを先に提示する。詳細レイアウトや画像生成へはまだ進まない。

## アウトライン

`cps-midterm` の標準の対応は以下。今回の研究に合う章名へ調整してよいが、研究全体のねらい・方法と評価・確認済みの結果・今後を区別する順序を保つ。

結果がまだない計画発表では、結果章を実在する設計案・検証計画などへ置き換える。標準の章を埋めるために結果を作らず、章名・目次・まとめを今回の内容に合わせる。

| 節 | 企画書との対応 |
|---|---|
| 01 研究のねらい | 世界観、利用・研究場面、前提、関連研究、今回の範囲 |
| 02 しくみと評価方法 | 作戦、システム・手法、評価の問いと方法 |
| 03 ここまでの結果 | 成果、結果から分かること、その限界 |
| 04 今後の展望 | 教訓を踏まえた設計・検証の計画、未完了事項と実施順 |
| まとめ（章外） | 4章それぞれの要点を同じ順に1行ずつ示し、Main findingsを回収 |

`cps-midterm` では表紙の後に画像付き2×2目次を置き、各章の入口に上部型の章扉を置く。既に発表実績や進捗がある場合は、冒頭に「研究の現在地」を追加してよい。第1章の関連研究では、重要な研究を個別に示した後、同じ比較項目の表で自分の研究の位置を示す。研究名・比較項目・枚数は今回の文献から決める。

関連研究は、今回の問いへつながる根拠として選ぶ。実験研究なら「何を変え、何を調べ、何が示されたか」を対応させ、著者名の列挙だけで論拠にしない。システム研究なら、何をできるようにしたかと今回比較する違いを示す。原図で利用像をつかんでから比較表へ進む配置は [制作仕様](production.md) を参照する。

`cps-midterm` の4章の説明量は2：3：3：2を初期の目安とし、持ち時間と証拠の量から調整する。元の25MB・32枚・46枚へ固定しない。短時間発表でも目次は必須。章扉を省く場合だけ、その理由を制作記録に残し、4章の読み順と本文デザインを保持する。表紙を1として目次・章扉・本文・まとめ・補足へ連続する表示ページ番号を割り当てる。

### 短い研究発表の構成

`cps-workshop` は、問いを理解する前提 → 提案・方法・考え方 → 確認済みの知見または議論したい計画、という論理から章を選ぶ。3章や特定枚数を必須にしない。概念研究なら問い・概念・検証計画、質的研究なら問題・調査と観察・解釈、アルゴリズム研究なら問題・方法・比較結果など、今回の根拠に即して決める。

- 目次は縦配置を既定とし、章名・短い説明・最終表示順に基づくページ範囲を示す。
- 章扉は `none`／採用する章を明示する。短い発表で本文の小見出しが案内を担える場合は独立した扉を増やさない。
- 本編の終了ページには要点と必要な議論の問いを置き、題目・著者・指定された連絡先をまとめる。補足の後に同じサマリを再掲するかは独立した指定とする。
- 実機・UI・定量値がないことを不足とみなさない。研究者の解釈と発言、仮説と既知の知見、検証計画と結果をラベルや主張の時制で区別する。

両プロファイルとも表紙1からデッキ末尾まで連番を付ける。構成正本は章ID、順序、目次型、章扉、本編終了、補足、最終表示を管理し、番号と目次範囲を派生させる。Markdownの承認済み構成から機械用JSONへ転記する際は対応版を記録し、下流で修正した内容は構成正本にも戻す。両方を別々の正本として手編集しない。

### MBの作成

本文はMBの連結とする。本編は `MB-01`、補助は `BMB-01` のように別採番する。既存ID方式は保持してよい。各MBの内容は次の3項目だけにする。

```markdown
## 研究のねらい

### MB-01 現状

- 話題： 現状
- メッセージ： この話題で聴衆が抱く疑問への、簡潔で大切な答えを一つ書く。
- 補足： 納得感やインパクトを高めるため、何を図や根拠で見せるかの方針を書く。
```

話題は「現状」「理想」「課題」など、アウトライン内で役割を整理する言葉。メッセージは1つの主張。どちらも画面文言の確定稿ではなく、構成段階で意図を保ちながら自然なタイトル・本文へ整える。補足は情報の方針に留め、図の位置・サイズ等は構成段階へ送る。出典詳細や企画書との対応表は別見出し／コメントに置き、MBの3項目を膨らませない。

検討は以下の順で行う。

1. **話題だけを読む**：企画書に対する抜け・重複を確認する。
2. **メッセージだけを読む**：前後の論理がつながるか確認する。重要語や判断対象が初めて現れる箇所では、聴衆が前のページまでに必要な場面・概念を理解できるか点検する。唐突なら、前段の主文や具体例で橋渡しする。独立ページは、明確な役割が必要な場合に追加する。
3. **証拠と結論を往復する**：目的→方法→結果→限界の筋が読めるか、結果を強く言い過ぎていないか確かめる。限界は必要な場所へまとめ、全ページを否定文で重くしない。
4. **時間と章の重みを合わせる**：追加で膨らんだら本編／補助へ配分し直す。過去の25MBや章比率をそのまま使わない。
5. **IDと対応表を更新する**：削除・統合・再採番時は旧新対応を一度記録し、構成以降で古いIDを参照しない。

過去の発表コメントを使う場合は「指摘 → 直すMB → 残る確認」の対応を作る。表現で直せる問題と、追加実験が必要な問題を分ける。アウトライン修正だけで研究上の未解決事項まで解決したとしない。

## 使用者レビューによる工程の区切り

企画書を提示したら、使用者の現行版への了承を待ってからアウトラインを作る。アウトラインを提示したら、同様に了承を待ってからスライド構成と図の具体化へ進む。修正があれば修正版を再提示し、レビューを受け直す。詳細は [必須レビュー](../SKILL.md#対話と再開3回の必須レビュー) に従う。
